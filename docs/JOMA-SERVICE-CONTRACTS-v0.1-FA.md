# جوما — قرارداد خدمات و قواعد اجرایی، نسخهٔ ۰٫۱

تاریخ: ۲۰۲۶-۰۹-۲۶

## ۱. وضعیت و مرز این تحویل

**مصوب قبلی:** مدل دامنه و ERD، تفکیک نقش/شخص/نمایندگی، پذیرش اتمیک و ایجاد Case فعال، hold حداکثر ۱۵ دقیقه، یادداشت خصوصی فقط برای نویسنده، انتشار و مخاطب صریح، D34–36 و G01–16.

**پیاده‌شده در این تحویل:** مجموعهٔ predicateهای مستقل PHP در `joma-core/domain_rules.php` و آزمون‌های ساختگی. این‌ها نه سرویس کامل‌اند، نه endpoint عمومی و نه نسخهٔ قابل نصب برنامه.

**پیشنهاد اجرایی این سند:** ترتیب قفل‌ها، قالب خطاها، نحوهٔ replay و بارگذاری snapshot. انتشار این سند تصویب تصمیم دامنهٔ جدید نیست. روش اجرایی باید در adapterهای mysqli پیاده و با MariaDB واقعی آزمایش شود.

**هنوز باز:** جزئیات رضایت، بازگردانی نمایندگی، عمر دسترسی روان‌سنج، سیاست انتشار غیرگزارش و پیش از Case، رمزنگاری/کلید/بازیابی/انتقال یادداشت، اتصال آزمون خام، دفتر مالی/استرداد/سهم، سلسله‌مراتب پیکربندی، مسیرهای تأخیر پرداخت و NO_SHOW و مبدأ ساعت اصلاح. در این موارد پیش‌فرضِ اجازه نداریم.

## ۲. قرارداد مشترک

- ورودی HTTP آینده تنها شناسهٔ هدف و دادهٔ مجاز دستور است؛ actor، scope مؤثر، role، permission، انتشار، entitlement و زمان معتبر از بدنهٔ درخواست پذیرفته نمی‌شوند.
- شناسهٔ اصلی: UUIDv4 تصادفی با `random_bytes`؛ در DB، `BINARY(16)`. UUID متنی پایین‌حروف فقط نمایش استاندارد در لایهٔ قواعد است. شناسهٔ Lookup عدد مثبت unsigned است؛ adapter باید عدد رشته‌ای mysqli را پس از اعتبارسنجی محدوده به integer تبدیل کند، نه loose comparison.
- زمان: UTC با `DATETIME(6)`؛ منبع زمان دستور ساعت سرور DB است، نه مرورگر. بازهٔ اعتبار `[from, until)`، و در نقطهٔ انقضا مجوز/hold دیگر معتبر نیست. parser مرجع نیازمند PHP 64-bit است؛ این شرط هنوز روی هاست بررسی نشده است.
- `null` صریح با «فیلد بارگذاری نشده» یکسان نیست. مثلاً `restrictions=null` یعنی وضعیت محدودیت‌ها ناشناخته و deny؛ `[]` یعنی پرس‌وجوی معتبر واقعاً هیچ محدودیتی نیافته است.
- خروجی قواعد `{allowed: bool, code: string}` است. `allowed=true` فقط همان شرط را تأیید می‌کند، نه اجرای دستور یا افشای محتوا.
- کنترل دسترسی ترکیبی است: حساب معتبر + نقش انتخاب‌شده + رابطه/نمایندگی + منبع + محدوده + اختیار همان عمل. نقش‌های دیگر حساب به نقش جاری اضافه نمی‌شوند. شناسهٔ تصادفی جای کنترل دسترسی نیست.
- مجوز فعلی باید در هر درخواست دوباره بررسی شود؛ cache قدیمی پس از ابطال پذیرفته نیست. دریافت فهرست، جست‌وجو، شمارش، پیش‌نمایش، دانلود و API نیز باید همین مرزها را رعایت کنند.

### ۲٫۱. نگاشت snapshot به جدول‌ها — نه ایجاد ستون تازه

| تصویر قواعد | منبع آینده در DB / مسئولیت adapter |
|---|---|
| `account` | `joma_accounts`؛ فقط پس از اعتبارسنجی session، نه وجود سطر حساب |
| `membership`, `role_assignment` | `joma_memberships`, `joma_role_assignments`؛ join همان حساب، شخص و scope |
| `policy_status`, `permissions` | نتیجهٔ policy/allowlist سمت سرور برای **همان نقش**؛ ستون دلخواه یا مجوز ادعایی کاربر نیست |
| `assignment.scope_id`, `admission_status`, `linked_case_id` | join واگذاری با `joma_admissions`؛ این فیلدها همه در جدول assignment نیستند |
| Case + accepted/relationship therapist | join `joma_clinical_cases`, `joma_therapeutic_relationships`, `joma_responsibility_acceptances` و زنجیرهٔ پذیرش |
| hold | `joma_capacity_holds`؛ تخصیص‌های منابع جداگانه باید کامل بارگذاری شوند |
| resource/version/publication | join گزارش/نسخه/انتشار یا فرم/نسخهٔ پاسخ/انتشار؛ `kind`, `version_id`, `scope_id` تصویر نرمال‌شده‌اند |
| audience | `joma_report_publication_audiences` یا `joma_form_publication_audiences`؛ بدون تبدیل عضویت Case به audience |
| representation/actions/restrictions | `joma_representations` + سیاست اختیار هر عمل + تمام محدودیت‌های مرتبط در `joma_case_representation_restrictions` |
| `required_product_id`, `source_verified` | استخراج از سیاست نهایی محصول و اعتبارسنجی مرجع entitlement؛ هیچ‌یک ادعای مرورگر یا صرف وجود رسید پرداخت نیست |
| receipt payload hash | `joma_command_receipts.payload_hash`، از `BINARY(32)` به hex 64 برای predicate؛ کلید idempotency جداست |

join ناقص، اشتباه scope یا خواندن قدیمی را این قواعد به‌تنهایی کشف نمی‌کنند. به‌خصوص اتصال acceptance↔relationship↔Case، اختیار انتشار و اصالت entitlement وظیفهٔ adapter است. تست‌ها فعلاً درستی SQL این نگاشت را نمی‌سنجند.

## ۳. C01 — ورود با گذرواژه و انتخاب زمینهٔ نقش

**ورودی پیشنهادی:** شناسهٔ ورود تأییدشده + گذرواژه؛ سپس انتخاب role_assignment و scope از گزینه‌های مجاز سمت سرور. شمارهٔ تماس هویت شخص نیست و باعث ادغام خودکار نمی‌شود. بازیابی پیامکی برای بازنشانی گذرواژه است، نه ورود بدون گذرواژه.

**پیش‌شرط/کنترل لازم:** HTTPS، session امن با کوکی HttpOnly/Secure/SameSite، تعویض session ID هنگام ورود/تغییر زمینه، CSRF برای عملیات تغییردهنده، rate limit و پاسخ غیرقابل استفاده برای کشف حساب؛ `password_hash`/`password_verify`، عدم ثبت گذرواژه و کد بازیابی. اتصال session به حساب فعال و سیاست ابطال آن باید پیاده شود. عمر session و ذخیرهٔ token بازیابی در این تحویل نهایی نشده‌اند.

**خروجی:** زمینهٔ انتخاب‌شدهٔ مجاز یا منع یکنواخت؛ داشتن نقش اجرایی/بالینی دیگر آن را خودکار فعال نمی‌کند. دعوت درمانگر را از مرجع معتبر ثابت می‌کند و نباید با ورودی فرم درمانگر دیگری جایگزین شود.

**قواعد موجود:** `joma_rule_principal`, `joma_rule_context`, `joma_rule_window` فقط اعتبار snapshot جاری را می‌سنجند؛ ورود، password verification، session و recovery هنوز اجرا نشده‌اند. مسیر portal مراجعه‌کننده الزام عضویت سازمانی درمانگر ندارد.

**audit لازم:** ورود/شکست/خروج/تغییر زمینه/ابطال، بدون گذرواژه، token، پاسخ فرم یا متن بالینی. آزمون‌های فعلی: حساب قفل‌شده، scope اشتباه، عضویت پایان‌یافته، نقش فرد دیگر، انقضا و ابطال و عدم تجمیع اختیار نقش‌ها.

## ۴. C02 — پذیرش مسئولیت و ساخت ClinicalEngagement

**ورودی:** assignment_id، هدف/زمینهٔ معتبر Case، مشارکت‌کنندگان اعتبارسنجی‌شده، کلید idempotency. actor از session است؛ شخص مسئول از assignment قفل‌شده.

**پیش‌شرط مصوب:** واگذاری `ASSIGNED` و پذیرش مربوط `AWAITING_THERAPIST`، Case متصل ندارد؛ پذیرنده خود درمانگر تعیین‌شده است و اختیار فعلی در محدوده دارد. تخصیص≠پذیرش. سیاست خدمت/offering، صلاحیت درمانگر و محدوده/هدف Case باید بررسی شوند. منشی نمی‌تواند به‌جای درمانگر قبول کند. پول/رضایت ممکن است خدمت را متوقف کند، نه ایجاد Case پس از پذیرش.

**نوشتن اتمیک پیشنهادی در یک transaction mysqli:**

1. کنترل هویت و مجوز اولیه؛ ثبت/قفل receipt دستور؛ سپس قفل مبانی اختیار مرتبط و خواندن جاری آن‌ها.
2. قفل Admission و Assignment به ترتیب ثابت؛ بررسی مجدد وضعیت، scope و ارتباط‌ها.
3. درج `joma_responsibility_acceptances` با actor=therapist؛ ایجاد `joma_therapeutic_relationships ACTIVE`؛ ایجاد `joma_clinical_cases ACTIVE`، مشارکت‌کنندگان و context عملیاتی معتبر.
4. تغییر assignment به `ACCEPTED`، admission به `LINKED_TO_CASE` و درج case_id؛ ثبت رویداد پذیرش و فعال‌شدن، حتی در حالت درمانگر مستقل با actor واحد.
5. ثبت نتیجهٔ receipt و audit در همان transaction؛ commit. هر شکست پیش از commit باید **همه** را rollback کند. اعلان بیرونی فقط پس از commit/از notification intent انجام شود.

**خروجی پیشنهادی:** شناسه‌های acceptance/relationship/Case و حالت ACTIVE؛ نه دادهٔ بالینی کامل. شناسه‌های جدید قبل از commit تضمین نتیجه نیستند.

**رقابت:** دو پذیرش با کلیدهای متفاوت نیز باید روی Admission serialize شوند؛ UNIQUE assignment به‌تنهایی جای این قفل را نمی‌گیرد. دعوت یا assignment جدید حق بازنویسی مسئول قبلی را ندارد. حالت solo می‌تواند یک کنش UX باشد ولی واگذاری/پذیرش رویدادهای جدا دارد؛ شاخهٔ solo بدون assignment در predicate فعلی پیاده نشده است.

**قاعدهٔ موجود:** `joma_rule_accept_assignment`. آزمون‌ها تنها guard و خطاهای actor/حالت را می‌سنجند؛ ایجاد واقعی Case و rollback هنوز آزموده نشده است.

## ۵. C03 — نگه‌داشت موقت ظرفیت و تأیید نوبت

**ورودی hold:** case_id، offering_id، بازهٔ زمانی و request_id اختیاری، کلید idempotency. فهرست منابع لازم و policy_version از سیاست معتبر سمت سرور استخراج می‌شود؛ مشتری حق حذف اتاق/درمانگر از آن را ندارد. TTL مثبت و حداکثر ۹۰۰ ثانیه، بدون تمدید خاموش در replay.

**پیش‌شرط:** Case و رابطه هر دو ACTIVE با مسئول پذیرفته‌شده؛ اختیار booking برای خود شخص/نماینده/منشی محدود و مبانی معتبر آن؛ رابطهٔ offering/policy/service/provider/scope و ساعات ارائهٔ خدمت. قبل از پذیرش فقط ترجیح زمانی، نه hold یا CONFIRMED. past booking، پیش‌نیازها و مسیر تأخیر طبق سیاست نهایی‌اند؛ predicate فعلی صرفاً طول بازه و TTL را می‌سنجد و آن‌ها را مجاز اعلام نمی‌کند.

### قرارداد ضد رزرو هم‌زمان — هنوز پیاده/آزموده نشده

تمام مسیرهای تغییر ظرفیت، شامل hold/confirm/release/expire/reschedule/cancel، باید یک ترتیب مشترک قفل داشته باشند: receipt → مبانی اختیار با ترتیب ثابت → Caseهای درگیر با ترتیب UUID → `joma_schedule_resources` مرتب‌شده با UUID → سطرهای hold/appointment. فهرست منابع را ابتدا بدون قفل می‌توان کشف کرد، اما پس از قفل باید دوباره اعتبارسنجی شود؛ اگر عوض شده، rollback/retry، نه افزودن قفل خارج از ترتیب. انتها/ابطال اختیار نیز باید بر همان مبنا serialize شود. deadlock همچنان ممکن است و نیازمند retry محدود کل transaction است.

- منبع درمانگر برای هر درمانگر در یک نصب مشترک است؛ scope مرکز دیگر نباید تداخل همان درمانگر را پنهان کند. این به معنی sync میان نصب‌های مستقل نیست.
- پس از قفل منبع، با **خواندن جاری قفل‌دار**، نه snapshot قدیمی REPEATABLE READ، تداخل تمام تخصیص‌های منابع بررسی شود: `existing.starts_at < requested.ends_at AND requested.starts_at < existing.ends_at`.
- hold تنها وقتی مانع است که `status=HELD AND expires_at>db_now`. نبود سطر allocation به معنی امکان اتکا به gap lock نیست؛ قفل سطر پایدار resource ضروری است. فهرست وضعیت‌های نوبت مانع ظرفیت باید صریح و آزموده باشد؛ حذف تاریخچه یا آزادسازی با حدس مجاز نیست.
- `db_now` پس از انتظار برای قفل گرفته شود. برابر زمان انقضا، hold دیگر قابل مصرف نیست. پاک‌سازی دوره‌ای شرط آزادشدن ظرفیت نیست.
- hold و تمام `joma_hold_allocations` به همراه receipt/audit اتمیک درج شوند. resource allocation باید دقیقاً با بازهٔ hold سازگار باشد؛ CHECK و index فعلی این برابری یا نبود overlap را تضمین نمی‌کنند.

**تأیید:** hold معتبر همان Case/offering، اختیار فعلی و تمام پیش‌نیازهای خدمت دوباره بررسی شود. منابع و بازه از hold قفل‌شده، نه body جدید؛ تداخل با منابع دیگر دوباره بررسی شود، با حذف فقط hold خود دستور. ساخت appointment=`CONFIRMED` و تخصیص‌ها، تبدیل hold به `CONSUMED`، audit و receipt یک commit است. دو تأیید یک hold تنها یک نوبت می‌سازند؛ UNIQUE hold و command دفاع تکمیلی‌اند.

انقضای hold رابطه را پایان نمی‌دهد. لغو نوبت رابطه را حذف نمی‌کند؛ نوبت لغوشده برای بازگشت، رزرو مرتبط جدید می‌خواهد. ENDED+CLOSED باز نمی‌شوند. Session بدون Appointment با Case/درمانگر معتبر ممکن است؛ این قرارداد Session را خودکار ایجاد نمی‌کند.

**قواعد موجود:** `joma_rule_active_engagement`, `joma_rule_hold_terms`, `joma_rule_intervals_overlap`, `joma_rule_confirm_hold`. خروجی `null` overlap یعنی ورودی نامعتبر، نه «زمان آزاد». این توابع مجوز booking یا ظرفیت را نمی‌سنجند.

## ۶. C04 — خواندن گزارش/فرم و یادداشت خصوصی

**ورودی خواندن:** شناسهٔ منبع/نسخه؛ actor فقط از session. تصویر انتشار و audience باید از join معتبر همان نسخه، Case و scope ساخته شود. نام فایل یا پسوند PDF نوع محتوا/مجوز را عوض نمی‌کند.

**زنجیرهٔ portal:** سیاست نهایی شناخته‌شده → نسخهٔ مجاز و غیرپیش‌نویس → انتشار PORTAL معتبر و غیرآینده → مخاطب صریح همان شخص → مبنای مستقیم یا نمایندگی معتبر → نبود منع مرتبط Case/service → entitlement معتبر در صورت الزام محصول.

- «عضو Case»، «پرداخت‌کننده»، «والد»، «مدیر» و «درمانگر دیگر» به‌خودی‌خود audience نیستند. عضو تازه به تاریخچه دسترسی خودکار نمی‌گیرد.
- گزارش بارگذاری‌شده با گزارش بررسی/منتشرشده یکی نیست؛ فقط درمانگر مسئول اختیار انتشار گزارش دارد. حق upload روان‌سنج حق انتشار یا دیدن کل Case نیست.
- پاسخ DRAFT فقط در مسیر جداگانهٔ ثبت‌کننده/درمانگر مسئول بررسی می‌شود؛ predicate portal همواره آن را رد می‌کند. مسیر ویرایش/خواندن بالینی draft هنوز نوشته نشده است.
- تست `FORM_RESPONSE` با `policy_status=APPROVED` فقط یک سیاست فرضیِ صریح را شبیه‌سازی می‌کند؛ مجوز عمومی انتشار فرم یا تعیین سیاست بازِ غیرگزارش نیست. پیش از Case و انواع ناشناخته در این predicate فعلاً deny هستند، نه ممنوعیت دائمی دامنه.
- پروتکل و نمرهٔ خام در portal مستثنا هستند؛ بسته‌بندی به صورت PDF راه دورزدن نیست. تعیین نوع واقعی فایل/ساختار و پالایش خروجی وظیفهٔ pipeline محتوای آینده است.
- در نمایندگی، شخص نماینده، موضوع نمایندگی، مخاطب، scope و عمل `document.read` باید تطبیق داشته باشند. تمام محدودیت‌های مرتبط باید بارگذاری شوند؛ suspension همان Case یا خدمت دسترسی مبتنی بر نمایندگی را فوری قطع می‌کند، نه همهٔ پرونده‌های آن کودک. بازگردانی در این نسخه اختراع نمی‌شود.
- entitlement باید برای محصول و ذی‌نفعِ معتبر استخراج شود؛ پرداخت تنها نه انتشار است، نه audience. دسترسی حرفه‌ای مستقل درمانگر از مسیر جداست و به خرید بیمار وابسته نمی‌شود. نگاشت سیاست محصول/subject در adapter هنوز پیاده نشده است.
- ابطال انتشار/نمایندگی/مخاطب یا پایان entitlement باید روی دانلودهای بعدی اثر کند؛ نشست باز، لینک ذخیره‌شده یا cache مجوز دائمی نیست. فایل حفاظت‌شده خارج از مسیر عمومی، با authorization هنگام دانلود، بدون URL دائمی عمومی و بدون cache مشترک ارائه شود. دادهٔ قبلاً تحویل‌گرفته‌شده یا screenshot قابل پس‌گرفتن تضمینی نیست.

**یادداشت خصوصی:** `joma_rule_private_note_author` فقط تطابق نویسنده با شخص حساب معتبر است؛ عضویت مرکز قبلی شرط نگهداری تاریخچهٔ نویسنده نیست. مدیر—even با نقش بالینی—، مراجعه‌کننده، نماینده یا درمانگر جدید استثنا نیستند. metadata نیز محدود است. این تابع کلید، رمزگشایی، vault ویندوز، sync ciphertext، durable acknowledgment یا بازیابی را اجرا نمی‌کند. هیچ plaintext خصوصی در این تحویل ذخیره نمی‌شود.

## ۷. C05 — idempotency، خطا و audit

**پیشنهاد اجرایی:** کلید idempotency تصادفیِ مستقل از payload، با حد طول ورودی؛ hash باینری ۳۲ بایتی برای lookup `(scope_id,idempotency_key)`. payload hash از ساختار canonical و allowlisted دستور ساخته شود، نه از ترتیب دلخواه JSON، secrets یا زمان جاری. نسخهٔ canonicalization باید ثابت و آزموده باشد؛ هنوز کد آن نوشته نشده است.

درج receipt در transaction با UNIQUE؛ برخورد با کلید موجود یعنی خواندن قفل‌دار آن و تطبیق command/actor/scope/hash. `SUCCEEDED` فقط با **مجوز فعلی نسبت به نتیجه** قابل replay است؛ مجوز replay به وضعیت ورودی قبلی ASSIGNED/HELD وابسته نیست، وگرنه replay موفق ذاتاً ناممکن می‌شود. کلید یکسان با payload متفاوت → conflict، بدون mutation. PROCESSING → انتظار محدود/پاسخ تکرارپذیر، نه اجرای موازی دوم. rollback کل transaction receipt ناتمام همان اجرا را نیز برمی‌گرداند. ثبت ردشدن‌ها و audit شکست باید قرارداد جدا داشته باشد و نباید موجب ثبت نیمه‌موفق عملیات دامنه شود.

**قاعدهٔ موجود:** `joma_rule_retry` فقط سازگاری رکورد انتخاب‌شده را می‌سنجد؛ lookup صحیح کلید، hash کردن، atomicity، احراز هویت و مجوز تازهٔ نتیجه را اجرا نمی‌کند.

**نگاشت خطای پیشنهادی برای HTTP آینده:** 401 نبود session معتبر؛ 403 منع زمینه/عمل بدون افشای منبع؛ 404 یکنواخت برای منبع غایب/غیرمجاز؛ 409 تعارض حالت/ظرفیت/idempotency؛ 422 ورودی نامعتبر؛ 429 محدودیت تلاش؛ 503 خطای گذرا پس از retry محدود. خطای SQL/stacktrace/وجود Case دیگر به مشتری داده نشود. کد داخلی predicate لزوماً متن یا status نهایی HTTP نیست.

**audit:** actor واقعی، نقش انتخاب‌شده و مبنای اختیار، scope، command/target، action/result/reason و زمان سرور؛ بدون متن خصوصی، جواب فرم، گذرواژه، token، کلید رمز یا لینک قابل دانلود. پذیرش، انتشار، تحویل حضوری، تعلیق و ابطال رویدادهای متمایزند. گزارش آزمون ساختگی audit درمانی نیست.

## ۸. گام بعد و معیار اتمام integration

به‌ترتیب: adapter خواندن معتبر → session/password و انتخاب زمینه → transaction پذیرش → قفل منابع و hold/confirm → انتشار/دانلود کنترل‌شده. هر مرحله با دادهٔ ساختگی، بدون اتکا به برنامهٔ قدیمی `clinic_*`.

آزمون‌های اجباری آینده روی MariaDB واقعی و حداقل دو اتصال مستقل:

1. دو پذیرش هم‌زمان با کلید یکسان و متفاوت: فقط یک engagement؛ خطا در هر مرحله: صفر رکورد نیمه‌کاره.
2. دو hold متداخل، حتی از دو مرکز برای یک درمانگر: فقط یک موفقیت؛ بازهٔ مجاور مطابق قرارداد.
3. confirm هم‌زمان، confirm در مرز انقضا، و انتظار برای قفل تا بعد از انقضا: بدون مصرف دوباره/دیرهنگام.
4. race پایان Case، ابطال role/نمایندگی و suspension با hold/read؛ تصمیم بر اساس وضعیت معتبر هنگام اجرای دستور، نه snapshot قدیمی.
5. deadlock/retry با همان کلید؛ قطع اتصال نزدیک commit و بازیابی نتیجه بدون تکرار mutation.
6. list/search/count/download/API با role، scope، audience، پیش‌نویس و entitlement؛ عدم نشت از مسیر جانبی.
7. ورود/خروج، بازیابی گذرواژه، CSRF، rate limiting، session fixation، ابطال نشست و خروجی خطای عمومی.

**هیچ‌یک از موارد این فهرست در تحویل حاضر «انجام‌شده» علامت نمی‌خورد.** تمام داده‌های قدیمی DB و پوشهٔ قدیمی هاست بنا بر اجازهٔ کاربر آزمایشی و قابل حذف‌اند؛ این تحویل برای توسعهٔ محلی نیازی به حذف یا تغییر هاست ندارد.
