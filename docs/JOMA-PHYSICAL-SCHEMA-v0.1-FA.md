# جوما — Physical Schema & MySQL DDL v0.1

**وضعیت:** نامزد طراحی و اجرای آزمایشی روی پایگاه دادهٔ تازه؛ نه بستهٔ ارتقای سامانهٔ فعلی و نه آمادهٔ نصب روی هاست واقعی.
**مبنا:** Logical ERD v0.1، تصمیمات مصوب قبلی و سه تأیید جدید کارفرما: رابطه اختیاری یک‌به‌یک Session/Appointment؛ مخاطب صریح پاسخ فرم؛ شناسهٔ تصادفی برای جداول اصلی.
**پشته قطعی:** PHP ماژولار/تابع‌محور + mysqli + MySQL/InnoDB. PostgreSQL، PDO، Composer، ORM، shell یا سرویس دائمی جزء پیش‌نیاز اجرای محصول نیستند.

## ۲. سازگاری محیط و گیت اجرا

**خط پایهٔ این DDL: Oracle MySQL 8.0.16 یا جدیدتر، با CHECKهای واقعاً enforce‌شده.** این حداقل برای نامزد حاضر انتخاب شده چون XOR اختیار، وضعیت‌های سازگار و شرط مقصد بانکی به CHECK تکیه دارند. نسخهٔ واقعی هاست هنوز بررسی نشده است؛ این سند ادعای سازگاری تأییدشده با آن نمی‌کند.

- MySQL 5.7 با اینکه JSON دارد، CHECK را مانند این طرح enforce نمی‌کند؛ این فایل برای آن تأیید نشده است.
- MariaDB معادل خودکار MySQL/JSON نیست و پشتیبانی این فایل برای آن ادعا نشده است.
- بررسی پیش از تست: `SELECT VERSION(), @@version_comment, @@sql_mode;` و پشتیبانی InnoDB/JSON/charset و مجوز CREATE/ALTER/REFERENCES. بررسی روی پایگاه آزمایشی با داده ساختگی انجام شود.
- اگر میزبان شرط حداقل را ندارد، اجرای شِما متوقف می‌شود؛ حذف CHECKها یا غیرفعال‌کردن Foreign Key راه‌حل مجاز نیست. باید میزبان مناسب یا نسخهٔ سازگارِ جدا با راه کنترل معادل طراحی شود.
- DDL با `SET NAMES utf8mb4 COLLATE utf8mb4_unicode_ci` و timezone نشست `+00:00` آغاز می‌شود. برنامه نیز باید `mysqli_set_charset` و timezone اتصال را درست تنظیم کند؛ تنظیم فایل واردکردن، همه اتصال‌های آینده را تنظیم نمی‌کند.
- Strict SQL mode باید برای محیط آزمایشی/اجرایی کنترل شود؛ قطع بی‌صدای داده/تبدیل نامعتبر قابل قبول نیست. حداقل PHP محصول هنوز باید جدا تعیین شود.

**DDL در MySQL auto-commit دارد.** اجرای ناقص با ROLLBACK همه جدول‌ها را برنمی‌گرداند. این فایل نه migration idempotent است و نه دستور rollback مخرب دارد. اگر اجرا شکست خورد، خروجی را نگه دارید و در یک پایگاه آزمایشی تازه علت را بررسی کنید؛ روی داده زنده تکرار کور انجام نشود.

## ۳. انتخاب شناسه و نوع داده

### کلید اصلی

- جدول اصلی/رویدادی: `BINARY(16)` با UUIDv4 تصادفیِ تولیدشده توسط برنامه و مولد رمزنگارانه معتبر.
- جدول تعریف/Lookup: `INT UNSIGNED AUTO_INCREMENT` با `code` پایدار و یکتا؛ مانند نقش، خدمت، روش پرداخت، محصول و تعریف تنظیم.
- UUIDv4 برای این نسخه انتخاب شده، نه «UUID یا ULID» مبهم. ULID زمان تولید را آشکار می‌کند؛ MySQL `UUID()` نیز جایگزین تولید UUIDv4 تصادفی برنامه نیست.
- هیچ DEFAULT تصادفی وابسته به DB در ID نیست. لایه PHP باید بایت‌های تصادفی معتبر، بیت‌های version/variant و تبدیل استاندارد را کنترل کند. صفرهای ساختگی، timestamp به‌عنوان ID یا تولید با rand ممنوع‌اند.
- در URL/API نمایش متنی canonical استفاده می‌شود؛ ورودی باید دقیقاً parse و به ۱۶ بایت تبدیل شود. binary خام در URL قرار نمی‌گیرد. mysqli پارامتر binary را با binding مناسب و بدون الحاق مستقیم SQL منتقل می‌کند؛ اعداد پول نیز با رشته اعشاری معتبر، نه float، ارسال شوند.
- UUIDv4 سخت‌تر حدس‌زده می‌شود ولی **کنترل دسترسی نیست**. هر درخواست، مجوز/منبع/Scope/تعلیق را بررسی می‌کند. اگر شناسه از لاگ/لینک نشت کرد، نباید دسترسی ایجاد شود.

### زمان، متن و JSON

- زمان رخداد/بازه: `DATETIME(6)` با قرارداد UTC. نمایش جلالی و منطقه زمانی در رابط، نه تغییر معنای ستون.
- کدهای داخلی حساس به بزرگی/کوچکی: ASCII و `ascii_bin`؛ متن فارسی: utf8mb4_unicode_ci. رمز عبور hash است، نه رمزنگاری برگشت‌پذیر.
- تعریف فرم: `form_versions.schema_json` از نوع JSON؛ پاسخ: `form_submission_revisions.answers_json` از نوع JSON.
- JSON معتبر به معنی داده معتبر فرم نیست؛ نسخه فرم، نوع فیلد، محدوده و مخاطب در سرور کنترل می‌شوند. Person/Case/Respondent/Author/Audience و مبنای اختیار در FKهای مستقل‌اند، نه داخل JSON بدون یکپارچگی.
- نسخه منتشرشده درجا تغییر نمی‌کند؛ این قرارداد به فرمان‌های برنامه/آزمون نیاز دارد و صرف JSON یا FK آن را enforce نمی‌کند.
- شناسه Account و Contact برای Person اجباری نیست. Account قفل‌شده نیز در قاعده یک حساب جاری شمرده می‌شود تا قفل امنیتی با ساخت حساب دوم دور زده نشود؛ INACTIVE تاریخچه است.

## ۴. سه تأیید جدید و اعمال فیزیکی آن‌ها

### ۴.۱ Session و Appointment

در `joma_clinical_sessions`:
- `appointment_id BINARY(16) NULL`
- `UNIQUE (appointment_id)`
- FK مرکب `(appointment_id, case_id, clinician_person_id)` به همان سه مشخصهٔ نوبت.
- FK مستقل `(case_id, clinician_person_id)` به Case/مسئول، حتی وقتی appointment_id تهی است.

بنابراین هر Session صفر یا یک نوبت و هر Appointment صفر یا یک Session دارد. MySQL چند NULL در UNIQUE را می‌پذیرد؛ چند جلسه مستقل بدون نوبت، با شناسه‌های جدا مجازند، نه چند جلسه برای همان نوبت.

جلسه بدون نوبت باید Case و درمانگر معتبر داشته باشد؛ نمونهٔ مراجعه فوری، مجوز ضمنی دورزدن رضایت/نمایندگی/شرط مالی نیست. `COMPLETED` شدن نوبت و ثبت جلسه در فرمان مناسب هماهنگ می‌شوند. NOT NULL/FK تضمین نمی‌کند هر نوبت انجام‌شده حتماً Session دارد؛ این تعهد جریان ثبت انجام است.

خروج جلسه گروهی هم‌زمان چند مراجع به معنی حذف زوج/خانواده نیست: چند شرکت‌کنندهٔ مصوب در **یک Case زوج/خانواده و یک جلسه** همچنان در دامنه است. مدل چند Case مستقل در یک نوبت گروهی پیاده‌سازی نشده است.

### ۴.۲ مخاطب پاسخ فرم

الگوی PublicationAudience برای فرم‌ها به صورت **روابط تایپ‌شده مستقل** پیاده شده:
- `form_publications` → نسخه مشخص پاسخ و Case مربوط؛
- `form_publication_audiences` → `recipient_person_id` صریح؛
- الگوی هم‌معنا برای گزارش: `report_publications` و `report_publication_audiences`.

این تصمیم حفظ همان الگو است، نه FK چندشکلیِ بدون کنترل به هر جدول. هر Audience به Publication واقعیِ نوع مربوط FK دارد. مبنای دریافت مستقیم یا نمایندگی، با CHECK و FK مرکب به نماینده/موضوع/Scope مشخص متصل است. قالب، عضویت Case یا فرم مشترک، Audience خودکار تولید نمی‌کنند.

**Draft:** دسترسی به ثبت‌کنندهٔ مجاز همان پاسخ و درمانگر مسئولِ دارای زمینه معتبر محدود است؛ واژهٔ درمانگر به همه افراد دارای نقش بالینی تعمیم ندارد. ثبت‌کننده باید هنگام ایجاد/ویرایش اختیار معتبر داشته باشد و لغو نمایندگی/مجوز در خواندن بعدی بررسی شود. این قاعده استثنا برای دیدن PrivateNote یا خام آزمون از مسیر فرم عمومی نیست.

ارسال نهایی، انتشار نیست. برنامه باید قبل از ایجاد Publication، SUBMITTED/CORRECTION بودن نسخه، اختیار انتشار، Case/موضوع، مخاطب و محدودیت جاری را کنترل کند. FK به‌تنهایی status والد را کنترل نمی‌کند. مرجع دقیق انتشار فرم غیرگزارشی اگر با درمانگر مسئول متفاوت باشد هنوز نیازمند قاعده صریح است؛ هیچ مجوز ادمین پیش‌فرض ایجاد نشده است.

این نسخه فقط انتشار بالینی در Case معتبر را از `form_publications` می‌پذیرد؛ فرم پذیرش پیش‌پرونده همچنان می‌تواند ذخیره شود ولی انتشار پورتال پیش‌پرونده از این جدول مجوز داده نشده است. سیاست آن مسیر در صورت نیاز جداست.

### ۴.۳ پذیرش پیش‌پرونده

`case_id` در admissions، appointment_requests و form_instances nullable است. مسیر تشکیل Case اولیه:
۱. پذیرش اجرایی/هویت معتبر؛ ۲. قبول مسئولیت توسط درمانگر؛ ۳. Acceptance + Relationship + Case و اتصال Admission در یک تراکنش.

FKهای مرکب مانع عدم تطابق درمانگر Assignment/Acceptance/Relationship/Case و جلسه/نوبت می‌شوند. حداقل یک Case برای هر Relationship با FK یک‌طرفه ثابت نمی‌شود؛ فرمان اتمیک باید هر دو را ثبت کند. هیچ FK معوق یا پرونده id=0 طراحی نشده است.

## ۵. یکپارچگی اعمال‌شده در DB و مسئولیت برنامه

| قاعده | DB این نسخه | کنترل تکمیلی لازم |
|---|---|---|
| یک حساب جاری برای Person | ستون generated + UNIQUE؛ ACTIVE و LOCKED | راهبرد حساب و بازیابی مجاز |
| یک ارجاع باز | generated open_admission_id + UNIQUE | دامنه Admission و مجوز تخصیص |
| اختیار بررسی دقیقاً مستقیم یا تفویض‌شده | CHECK XOR + FKهای Actor/Scope | اعتبار زمانی و اجازه همان عمل |
| مسئول Case با پذیرش سازگار | FKهای مرکب و UNIQUE رابطه | پذیرش واقعی و هماهنگی statusها |
| Session اختیاری یک‌به‌یک | UNIQUE nullable + FK مرکب | مجوز/شروط خدمت و انجام واقعی |
| مدت Hold | ترتیب زمان و سقف ۱۵ دقیقه با CHECK | پذیرش قبلی، ساعت جاری و کنترل ظرفیت |
| مخاطب صریح فرم/گزارش | Publication و Audience تایپ‌شده، FK مبنای نمایندگی | انتشار مجاز، رفع‌نشدن تعلیق و کنترل هر بار مشاهده |
| انتشار گزارش توسط مسئول Case | FK مرکب Case/Publisher | نسخه بررسی‌شده، Audience و استحقاق |
| دریافت بانکی دارای مقصد معتبر | CHECK + FK روش بانکی + FK فضای مالی/مقصد | اثبات وصول، واحد پول، مجوز ثبت و جلوگیری از تکرار خارجی |
| حفظ تاریخچه | همه FKها RESTRICT؛ جدول تغییر/نسخه | منع UPDATE/DELETE نامجاز، ممیزی و راه اصلاح |
| محرمانگی PrivateNote | نبود payload/answers/audience عمومی در reference | رمزنگاری سمت کاربر، کلید و کنترل نویسنده؛ هنوز پیاده‌سازی نشده |

همه Foreign Keyها `ON DELETE RESTRICT ON UPDATE RESTRICT` دارند. این مانع cascade مخرب است، اما اگر رکوردی هیچ فرزند نداشته باشد به‌خودی‌خود جلوی DELETE را نمی‌گیرد. حساب DB برنامه باید حداقل اختیار لازم داشته باشد؛ mutationها از فرمان کنترل‌شده عبور کنند. append-only در برابر مالک هاست/DB تضمین مطلق نیست.

## ۶. جلوگیری از تداخل نوبت — ایندکس کافی نیست

ایندکس‌های `(resource_id, starts_at, ends_at, ...)` سرعت یافتن تداخل را بهتر می‌کنند. `UNIQUE(resource_id, starts_at)` تنها شروع یکسان را می‌گیرد؛ بازه ۱۰:۰۰–۱۱:۰۰ با ۱۰:۳۰–۱۱:۳۰ همچنان هم‌پوشانی دارد. MySQL در این DDL exclusion constraint بازه‌ای ندارد.

### قرارداد الزامی فرمان رزرو/جابجایی/مصرف/آزادسازی

۱. تراکنش آغاز شود؛ مجوز/پذیرش/Case و منابع موردنیاز مشخص شوند.
۲. ردیف‌های `schedule_resources` مربوط، در ترتیب ثابت شناسه قفل شوند (`SELECT ... FOR UPDATE`). **همه** مسیرهای تغییر ظرفیت باید همین قرارداد را رعایت کنند؛ حتی رزرو دستی و آزادسازی.
۳. بعد از قفل، تداخل با خواندن جاری و قفل‌دار بررسی شود؛ نه snapshot قدیمیِ خوانده‌شده پیش از قفل. بازه‌ها نیمه‌بازند: `[starts_at, ends_at)`؛ انتهای یک جلسه می‌تواند شروع جلسه بعد باشد.
۴. تداخل وقتی است که `existing.starts_at < requested.ends_at AND existing.ends_at > requested.starts_at`.
۵. نوبت‌های مؤثرِ لغونشده و Holdهای HELD با `expires_at > now_utc` در ظرفیت حساب شوند. مهلت منقضی به اجرای به‌موقع Cron وابسته نباشد.
۶. در تأیید، Hold خود عملیات فقط پس از اعتبارسنجی از تعارض با خودش مستثنا و در همان تراکنش مصرف شود؛ Hold دیگران مستثنا نشود. Appointment و Allocation و Request مرتبط هماهنگ ثبت شوند.
۷. در جابه‌جایی، منابع قدیم و جدید همگی پیشاپیش با ترتیب ثابت قفل شوند؛ اگر زمان جدید نامعتبر است، زمان قبلی حفظ شود.
۸. قبل از commit، نتیجه فرمان و ممیزی لازم ثبت شوند؛ سپس اعلان جدا. تماس بانک/SMS داخل تراکنش طولانی انجام نشود.
۹. deadlock/timeout باید rollback کامل و retry محدودِ همان قصد منطقی داشته باشد؛ retry نباید اثر/دریافت دوم بسازد. DB بدون اجرای این پروتکل از هم‌پوشانی جلوگیری کامل نمی‌کند.

برای جلوگیری از رزرو هم‌زمان یک درمانگر در دو مرکز، ScheduleResource درمانگر در همان نصب به Person یکتا متصل است؛ Scope عملیاتی نوبت جداست. سرویس دسترسی فقط «زمان آزاد نیست» را برای زمینه نامجاز بازمی‌گرداند، نه نام مراجع/مرکز دیگر. بین نصب‌های مستقل همگام‌سازی ظرفیت وعده داده نشده است.

V1 ظرفیت انحصاری هر منبع را هدف می‌گیرد؛ ظرفیت چندنفره/گروه چند Case مصوب نیست. زوج/خانوادهٔ یک Case می‌توانند همان منبع را برای یک جلسه اشغال کنند. کنترل ترتیب قفل باید در قرارداد همه فرمان‌های مرتبط یکسان باشد؛ این متن ادعای صفرشدن deadlock نمی‌کند.

## ۷. حفاظت محتوا و داده‌های خارج این نسخه

### نکات ذخیره

- report_text و message_body داده محافظت‌شدهٔ غیرعمومی‌اند، نه PrivateNote. کنترل دسترسی، حفاظت فایل/backup و امنیت سرور همچنان لازم است.
- `private_note_references` فقط metadata حداقلی و نویسنده‌محدود است. متن، JSON پاسخ، کلید، فایل عمومی و grant مخاطب ندارد. ثبت metadata برای مخزن محلی فقط در حد لازم انجام شود.
- جدول payload رمز‌شده، کلید، recovery و انتقال بسته‌شده هنوز نهایی نشده و عمداً جایگزین ناامن برای آن ساخته نشده است. این DDL پیاده‌سازی قابلیت یادداشت خصوصی نیست.
- جدول فرم عمومی فقط ADMINISTRATIVE/CLINICAL/CONSENT دارد؛ پروتکل خام تست یا PrivateNote در آن ذخیره نمی‌شود. تغییر نوع/JSON باید سمت سرور کنترل شود تا راه دورزدن باز نشود.
- فایل گزارش بیرون دسترسی وب عمومی، با کنترل نوع/اندازه و وضعیت QUARANTINED/READY است؛ MIME و پسوند به‌تنهایی امنیت یا «گزارش نهایی بدون خام تست» را ثابت نمی‌کنند.
- هیچ secret پیامک/درگاه در config_versions.value_json یا audit قبل/بعد قرار نمی‌گیرد؛ نگهداری امن رازها سند/پیاده‌سازی جدا می‌خواهد.

### بخش‌های عمداً ناتمام یا خارج این DDL

| بخش | علت |
|---|---|
| Charge/ReceiptAllocation/دفترکل/کیف‌پول/سهم | مدل تفصیلی مالی هنوز مصوب نیست؛ فقط واقعه دریافت و مقصد/پرداخت‌کننده تعریف شده |
| پروتکل و نمره‌گذاری خام آزمون | منتظر بسته نهایی و قرارداد ابزار؛ گزارش دستی مستقل پشتیبانی می‌شود |
| ciphertext/کلید/transfer یادداشت خصوصی | قرارداد crypto و recovery نهایی نشده؛ ذخیره متن آشکار جایگزین نشده |
| بازیابی نمایندگی/رفع تعلیق | اختیار و شروط آن هنوز باز؛ status قابل رفع خودکار اضافه نشده |
| جداول تبدیل داده‌های clinic_* | مهاجرت واقعی نیازمند نگاشت/پاک‌سازی/تست مستقل است |
| موتور دلخواه فرمول/قانون یا queue دائمی | خارج از معماری سبک و دامنه مصوب |

Receipt در این نسخه Payer شخص دارد؛ دریافت از سازمان و قرارداد طرف‌های غیرشخصی هنوز نیازمند تصمیم است. ارز/واحد مالی مشخص نشده و هیچ تبدیل ریال/تومان خودکار وجود ندارد. نبود جدول اتهام/سهم به معنی یکی‌بودن درآمد و دریافت نیست.

## ۸. مسیر بررسی و اجرای آزمایشی — برای کاربر غیرتخصصی

**اکنون این فایل را روی پایگاه واقعی کلینیک یا نصب موجود وارد نکنید.** نه config واقعی و نه داده موجود باید جایگزین شود.

۱. ابتدا نسخه MySQL میزبان مشخص شود؛ هیچ رمز یا کلیدی در گفتگو ارسال نشود.
۲. یک پایگاه آزمایشی تازه و خالی با دسترسی جدا ایجاد شود. کاربر محصول نیازمند shell یا Python نیست؛ phpMyAdmin در صورت پشتیبانی مجوزها کافی است.
۳. فایل SQL کامل در همان پایگاه آزمایشی وارد شود. در صورت خطا، متن خطا بدون رمز/داده شخصی ثبت شود؛ اجرای باقی فایل را موفق تلقی نکنید.
۴. وجود ۷۰ جدول و تمام ۱۷۳ FK، CHECKهای enforce‌شده و collation بررسی شود؛ SHOW CREATE TABLE برای چند جدول حساس کافیِ پوشش کامل نیست ولی نقطه شروع بررسی است.
۵. آزمون‌های رفتاری با داده ساختگی اجرا شوند: حساب جاری تکراری، XOR اختیار، ارجاع باز تکراری، Session دوم، مخاطب اشتباه، مقصد بانکی ناسازگار، هم‌زمانی ظرفیت، و تغییر/حذف نامجاز تاریخچه.
۶. پس از این مرحله، قرارداد API/فرمان‌ها و مجوزها پیاده و آزمون شوند. صرف import موفق، آماده‌بودن کلینیک برای استفاده نیست.

فایل CREATE TABLE بدون IF NOT EXISTS است تا اجرای دوباره روی schema متفاوت، اختلاف را پنهان نکند. rollback این نسخه حذف خودکار داده یا DROP کور نیست؛ روی محیط آزمایشی می‌توان یک DB تازه ایجاد کرد. برای تولید، migration افزایشی و نسخه‌دار جدا لازم است.

## ۹. وضعیت اعتبارسنجی این تحویل

- **انجام شده:** تولید تکرارپذیر؛ بررسی ۱۸ تست ساختاری Python شامل وجود و نوع FKها، candidate keyهای مقصد، ایندکس مبدأ، NULL/UNIQUE جلسه، XOR اختیار، جدایی PrivateNote و مخاطب تایپ‌شده.
- **انجام نشده:** اجرا یا parse واقعی MySQL؛ آزمون enforce شدن CHECK/UNIQUE/FK روی موتور؛ آزمون هم‌زمانی دو اتصال؛ آزمون mysqli/API/مرورگر؛ رندر بصری نمودارها؛ تست مهاجرت داده موجود.
- محیط فعلی MySQL Server/Client یا Docker ندارد. خروجی static test را گزارش PASS پایگاه داده یا تضمین امنیت نمی‌نامیم.

مسیر توسعه، فقط در محیط توسعه:

```text
python tools/generate-joma-schema.py
python tests/joma_schema_static.py
```

این ابزارهای توسعه روی هاست عملیاتی لازم نیستند. نمودارها از همان تعریف تولید می‌شوند تا مدل تصویری و SQL از هم جدا نشوند. حداقل نسخه PHP، نسخه واقعی MySQL هاست و موارد OPEN باید پیش از استقرار مشخص شوند.
