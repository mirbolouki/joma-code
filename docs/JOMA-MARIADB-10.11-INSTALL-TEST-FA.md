# جوما — راهنمای ایجاد و بررسی شِما روی MariaDB 10.11

## وضعیت محیط و این بسته

محیط اعلام‌شده توسط کارفرما:
- MariaDB `10.11.19-MariaDB-cll-lve`؛
- PHP در phpMyAdmin: `8.4.24`، mysqlnd، mysqli، curl و mbstring؛
- دیتابیس `mirbolouki_clinic` موجود و طبق اعلام کارفرما کاملاً خالی و آزمایشی است.

این اطلاعات به‌عنوان مشخصات هدف ثبت شد. هیچ اتصال یا اجرای راه‌دور توسط ایجنت انجام نشده است. بستهٔ مخصوص `database/joma-mariadb-v0.1` برای همین خانوادهٔ MariaDB تهیه شده؛ بسته Oracle MySQL قبلی بدون تغییر باقی مانده است. این تغییر تطبیق با موتور واقعی میزبان است، نه مهاجرت داده یا تغییر به PostgreSQL/PDO.

**تفاوت مهم:** JSON در MariaDB یک alias برای LONGTEXT با collation مناسب JSON و بررسی JSON_VALID است، نه ذخیرهٔ باینری بومی MySQL. نمایش LONGTEXT/utf8mb4_bin برای ستون JSON در phpMyAdmin طبیعی است؛ آن را دستی به collation متن معمولی تبدیل نکنید. STORED/PERSISTENT و ایندکس ستون محاسبه‌شده پشتیبانی می‌شوند؛ بازبینی فایل با این قابلیت‌ها انجام شده اما اجرای همین DDL روی موتور میزبان هنوز باید نتیجه بدهد.

مراجع فنی بازبینی:
- https://mariadb.com/docs/server/reference/data-types/string-data-types/json
- https://mariadb.com/docs/server/reference/sql-statements/data-definition/create/generated-columns

## فایل‌های لازم

| مسیر داخل بسته | کار |
|---|---|
| `database/joma-mariadb-v0.1/000_preflight_readonly.sql` | بررسی فقط‌خواندنی نسخه، نام DB، خالی بودن و فعال بودن قیود |
| `database/joma-mariadb-v0.1/001_core.sql` | ساخت ۷۰ جدول و ۱۷۳ FK برای MariaDB؛ فقط روی DB آزمایشی خالی |
| `database/joma-mariadb-v0.1/002_verify_readonly.sql` | شمارش و یافتن نام جدول/FK/CHECK گم‌شده؛ بدون تغییر داده |
| `database/joma-mariadb-v0.1/expected-schema.json` | فهرست انتظار برای تطبیق ساختار |
| `deploy/joma-db-check/joma-db-check.php` | ابزار موقت محافظت‌شده برای تست اتصال واقعی PHP و metadata؛ تست نوشتن اختیاری با rollback |
| `deploy/joma-db-check/expected-schema.json` | همراه ابزار موقت، فاقد رمز/داده بیمار |
| `deploy/joma-db-check/joma-db-check-config.example.php` | نمونه تنظیمات؛ فقط روی هاست و خارج document root تکمیل شود |

ابزار موقت نصب‌کننده یا خود برنامه جوما نیست و SQL را خودکار import نمی‌کند. هیچ ابزار توسعه، node_modules یا Python لازم نیست روی هاست آپلود شود.

## مرحله ۱ — انتخاب قطعی دیتابیس درست

۱. در phpMyAdmin از ستون چپ دقیقاً `mirbolouki_clinic` را انتخاب کنید.
۲. تب **SQL** را باز کنید؛ متن `000_preflight_readonly.sql` نسخهٔ MariaDB را اجرا کنید.
۳. نتیجه باید چنین باشد:
   - `selected_database`: دقیقاً `mirbolouki_clinic`؛ نه NULL یا نام دیگری؛
   - نسخه: MariaDB 10.11؛
   - `existing_base_tables`: صفر؛
   - InnoDB پشتیبانی شود؛
   - `foreign_keys_enabled` و `checks_enabled`: هر دو ۱؛
   - sql_mode شامل `STRICT_TRANS_TABLES` یا `STRICT_ALL_TABLES` باشد.

اگر جدول موجود بود یا نام DB اشتباه بود، هنوز import نکنید. خاموش‌کردن قیود یا حذف دادهٔ ناشناخته راه‌حل نیست. وجود UTF8 connection collation به‌تنهایی کافی نیست؛ charset/collation جدول‌ها را خود DDL تعیین می‌کند.

## مرحله ۲ — واردکردن شِما

۱. همان دیتابیس را انتخاب‌شده نگه دارید.
۲. تب **Import / درون‌ریزی** را باز کنید.
۳. فایل **`database/joma-mariadb-v0.1/001_core.sql`** را از بستهٔ جدید انتخاب کنید، نه نسخهٔ MySQL قبلی.
۴. قالب SQL و encoding UTF-8 باشد. گزینه‌ای برای نادیده‌گرفتن خطا یا خاموش‌کردن FK/CHECK فعال نکنید.
۵. اجرا را بزنید و پیام نهایی را بررسی کنید.

فایل از ابتدا نام دیتابیس را تغییر نمی‌دهد؛ انتخاب سمت چپ مهم است. داخل فایل، timezone نشست UTC و FK/CHECK روشن می‌شوند. DDL تراکنش rollbackشدنی نیست و implicit commit دارد. `CREATE TABLE` بدون IF NOT EXISTS است تا اجرای ناقص/تکراری پنهان نشود.

**اگر خطا رخ داد:** متوقف شوید؛ اولین پیام خطا و نام دستور/جدول را ثبت کنید. فایل را کورکورانه دوباره روی ساختار نیمه‌ساخته اجرا نکنید؛ FK checks را صفر نکنید. چون DB آزمایشی است، پس از تشخیص علت می‌توان برای تلاش بعدی DB خالی تازه آماده کرد؛ این بسته DROP/TRUNCATE یا پاک‌سازی خودکار ندارد.

هیچ رمز، Connection String، فایل config تکمیل‌شده یا اطلاعات مراجع را برای رفع خطا ارسال نکنید. متن خطای DDL معمولاً فاقد رمز است؛ پیش از ارسال بازبینی کنید.

## مرحله ۳ — بررسی ۷۰ جدول و روابط

در تب SQL، `002_verify_readonly.sql` را اجرا کنید.

| خروجی | انتظار |
|---|---|
| `joma_table_count` | ۷۰ |
| `innodb_count` | ۷۰ |
| `table_collation_count` | ۷۰ |
| PRIMARY KEY | ۷۰ |
| FOREIGN KEY | ۱۷۳ |
| UNIQUE | ۷۲، جدا از PRIMARY KEY |
| CHECK | حداقل ۹۰ قید صریح؛ MariaDB برای ۱۴ ستون JSON نیز قید اعتبارسنجی خودکار می‌افزاید؛ به شمار ثابت ۹۰ اکتفا نکنید |
| قوانین DELETE/UPDATE همه FKها | RESTRICT / RESTRICT |
| سه فهرست Missing expected ... | هر سه بدون سطر |

۷۰ جدول به‌تنهایی کافی نیست؛ ممکن است ساخت جدول‌ها موفق و بخشی از ALTER TABLEهای افزودن FK شکست خورده باشد. به فهرست FKهای گم‌شده توجه کنید.

SHOW CREATE TABLE برای فرم و پاسخ باید JSON_VALID و قید نوع object را نشان دهد. LONGTEXT در خروجی MariaDB خطا نیست. جدول accounts باید ستون generated و UNIQUE حساب جاری داشته باشد. clinical_sessions باید appointment_id nullable و UNIQUE داشته باشد.

## مرحله ۴ — ساخت کاربر اتصال، فقط داخل پنل هاست

نام دیتابیس با نام کاربر دیتابیس لزوماً یکسان نیست. در بخش مدیریت دیتابیس cPanel:
- کاربر DB واقعی را به `mirbolouki_clinic` متصل کنید؛ نام کامل با prefix پنل را به کار ببرید.
- برای import، کاربر اجراکننده به مجوزهای ساخت/تغییر/ارجاع نیاز دارد.
- برای ابزار **فقط‌خواندنی اتصال**، SELECT و امکان دیدن metadata جدول‌های خودش کافی است.
- برای تست rollback، کاربر آزمایشی موقت باید INSERT لازم نیز داشته باشد. ابزار دستور CREATE/DROP/ALTER اجرا نمی‌کند.
- کاربر دائمی برنامه در آینده باید کمترین مجوز موردنیاز را داشته باشد؛ برای راحتی، دسترسی DDL عمومی به کاربر برنامه ندهید.

رمز را فقط در تنظیمات محلی وارد کنید؛ لازم نیست آن را در چت یا repository ذخیره کنید.

## مرحله ۵ — تست اتصال واقعی PHP با ابزار موقت

نسخه PHP گزارش‌شده توسط phpMyAdmin ممکن است با PHP دامنه برنامه متفاوت باشد. ابزار زیر نسخه PHP **همان دامنه** و اتصال mysqli را نشان می‌دهد.

### چیدمان فایل‌ها

فرض کنید document root دامنه شما `/home/USER/public_html` است:

```text
/home/USER/joma-db-check-config.php             ← تنظیمات، خارج وب
/home/USER/public_html/joma-db-check.php        ← ابزار موقت
/home/USER/public_html/expected-schema.json     ← manifest بدون راز
```

اگر document root دامنه شما مثلاً `/home/USER/my` است، ابزار و manifest را در `my` و config را در `/home/USER` بگذارید. **ابزار باید در ریشه document root باشد، نه پوشه فرعی tools**؛ به‌صورت پیش‌فرض config را در والد `__DIR__` می‌خواند. والد باید واقعاً بیرون هر مسیر عمومی وب باشد. اگر ساختار هاست متفاوت است، مسیر خصوصی را پیش از ادامه مشخص کنید؛ config را داخل مسیر عمومی نگذارید.

### آماده‌سازی

۱. نمونه config را بیرون وب به نام `joma-db-check-config.php` قرار دهید؛ دسترسی فایل در صورت امکان `0600` باشد.
۲. فیلدهای host، port، نام کاربر و password را از پنل هاست پر کنید. host معمولاً localhost است ولی مقدار واقعی میزبان ملاک است. این host اتصال سمت سرور است، نه آدرس مرورگر.
۳. name همان `mirbolouki_clinic` بماند. ابزار نام متفاوت را نمی‌پذیرد.
۴. یک توکن تصادفی تازهٔ حداقل ۳۲ کاراکتری با password manager بسازید؛ در `access_token` بگذارید. **این توکن با رمز DB متفاوت است** و آن را در چت/URL قرار ندهید.
۵. `enabled` و `test_database_confirmed` را true کنید. `allow_rollback_tests` فعلاً false بماند.
۶. فایل PHP و manifest را در ریشه دامنه آپلود کنید. ابزار فقط HTTPS را می‌پذیرد؛ با HTTP یا بدون config معتبر باز نمی‌شود.
۷. آدرس `https://دامنه‌شما/joma-db-check.php` را باز کنید. توکن را در فرم رمزدار وارد و دکمه «بررسی اتصال و ساختار» را بزنید؛ رمز دیتابیس را در این فرم وارد نکنید.

### انتظار

PASS برای اتصال، MariaDB 10.11، strict mode، فعال بودن قیود، ۷۰ جدول و collation، نام/ستون/مقصد ۱۷۳ FK، ۹۰ CHECK صریح و ۷۲ UNIQUE با ستون‌های مربوط.

این آزمون هیچ داده‌ای نمی‌نویسد و هیچ نصب/مهاجرتی انجام نمی‌دهد؛ SET charset/timezone فقط نشست همان اتصال را تنظیم می‌کند. نمایش FAIL باید بررسی شود؛ چاپ ROLLBACK یا PASS اتصال، جای PASS همه بررسی‌ها نیست.

ابزار خطای خام SQL/رمز/مسیر config را نمایش نمی‌دهد؛ کد خطا را می‌توانید بدون داده محرمانه گزارش کنید. خطای ۱۰۴۵ معمولاً احراز هویت/مجوز و ۱۰۴۹ معمولاً انتخاب DB است؛ تفسیر قطعی نیازمند بررسی پنل است. اگر HTTPS توسط proxy میزبان پایان می‌یابد و ابزار آن را تشخیص نمی‌دهد، guard را حذف نکنید؛ تنظیم معتبر HTTPS میزبان باید بررسی شود.

## مرحله ۶ — تست اختیاری چند قید با داده ساختگی و ROLLBACK

فقط بعد از PASS مرحله قبل و با اطمینان از آزمایشی بودن DB، `allow_rollback_tests` را true کنید. صفحه را دوباره باز کنید و دکمه تست rollback را بزنید.

ابزار داخل یک تراکنش، چند Person/Account/Scope/Form مصنوعی ایجاد و موارد زیر را آزمایش می‌کند:
- رد Account جاری دوم برای یک Person با خطای UNIQUE؛
- رد Account با Person ناموجود با خطای FK؛
- رد status نامعتبر با CHECK؛
- رد مبنای اختیار که نه مستقیم است و نه تفویض‌شده؛
- پذیرش JSON object معتبر، رد JSON خراب و رد array به جای object.

در `finally`، ROLLBACK انجام می‌شود؛ داده ساختگی باقی نمی‌ماند. قطع اتصال با تراکنش باز InnoDB نیز آن را rollback می‌کند. هیچ DDL یا seed دائمی انجام نمی‌شود. این ابزار تست جامع ۷۰ جدول، Session، تداخل دو اتصال، مجوزهای API یا رمزنگاری نیست؛ آن تست‌ها مرحله بعد هستند.

**ابزار باید پس از پایان حذف شود:** PHP عمومی، manifest کنار آن و config خصوصی را پاک کنید و توکن موقت را کنار بگذارید. اگر خطایی رخ داده، پیش از حذف فقط خروجی غیرحساس لازم را نگه دارید. ابزار را به‌عنوان صفحه مدیریت دائمی رها نکنید.

## مرحله ۷ — معنی «اتصال برنامه» در این مرحله

فعلاً Schema جدید داریم، نه برنامه جدیدِ کامل با صفحه ورود، مجوز، فرمان‌های رزرو و فرم‌ساز. تست ابزار ثابت می‌کند PHP همان دامنه با mysqli به DB جدید وصل می‌شود و بخشی از ساختار درست است.

**کد فعلی clinic-app را صرفاً با عوض‌کردن config به دیتابیس خالی جدید وصل نکنید.** آن کد جدول‌های clinic_* را انتظار دارد؛ این بسته joma_* می‌سازد و سازگارکردن برنامه، پیاده‌سازی مستقل بعدی است. ابزار موقت نیز جای connection module نهایی برنامه را نمی‌گیرد.

اتصال نهایی برنامه تابع‌محور با mysqli، prepared statement، utf8mb4، UTC و مدیریت خطای غیر‌افشاگر خواهد بود. قفل‌گذاری رزرو، کنترل Session/Case و Audience در آن باید پیاده و تست شوند؛ وجود FK/UUID به‌تنهایی مجوز یا جلوگیری از تداخل نیست.

## اعتبارسنجی انجام‌شده توسط ایجنت

- تولید MariaDB از همان منبع ۷۰ جدول؛ حفظ ۱۷۳ FK با RESTRICT و ۹۰ CHECK صریح؛ روشن‌کردن CHECK/FK برای نشست import.
- تطبیق manifest جدول/FK/Unique و نگاشت ستون‌های FK برای ابزار اتصال.
- lint دو فایل PHP با PHP WASM **8.4.25**؛ موفق. این نسخهٔ ابزار توسعه است، نه اثبات اجرای PHP 8.4.24 هاست.
- بررسی‌های ساختاری قبلی ۱۸ مورد و بررسی‌های تطبیق بسته MariaDB؛ جدا از آزمون موتور.
- **اجرا نشده:** import روی MariaDB واقعی، تست اتصال به هاست، تست rollback روی موتور، رقابت دو اتصال، نصب یا اتصال خود برنامه.

پس از مراحل ۱ تا ۳، کافی است شمار جدول/FK/Unique، خالی بودن فهرست‌های Missing و اولین خطا در صورت وجود را بفرستید؛ نه فایل تنظیمات یا رمز.
