# نتیجهٔ پروب IP — پاسخ قطعی به الزام ۲۳

**تاریخ:** ۱۴۰۵/۰۷/۱۴ · **اجرا:** مالک، روی دیتای موبایل · **ابزار:** `phase5/tools/ip_probe.php`

---

## ۱. خروجی خام

```
REMOTE_ADDR     = 2.147.253.154
SERVER_ADDR     = 91.207.205.36
SERVER_SOFTWARE = LiteSpeed
PHP 8.1.34

هیچ هدر پروکسی‌ای وجود ندارد.
REMOTE_ADDR عمومی است؟ بله — احتمالاً سرور مستقیم است
IPv4 است. کل نشانی هش می‌شود.
```

هدرهای موجود فقط هدرهای عادی مرورگرند: `ACCEPT`، `ACCEPT_ENCODING`،
`ACCEPT_LANGUAGE`، `COOKIE`، `HOST`، `USER_AGENT`،
`UPGRADE_INSECURE_REQUESTS`، `SEC_CH_UA*`، `SEC_FETCH_*`، `PRIORITY`.

**هیچ‌کدام از اینها نیست:** `X-Forwarded-For`، `X-Real-IP`، `CF-Connecting-IP`،
`AR-Real-IP`، `True-Client-IP`، `Via`.

## ۲. چه چیزی ثابت شد

| یافته | شاهد | پیامد |
|---|---|---|
| **پروکسی معکوس یا CDN در کار نیست** | صفر هدر پروکسی؛ `REMOTE_ADDR` عمومی | `REMOTE_ADDR` قابل اتکاست |
| **IP واقعاً به اپراتور موبایل می‌رسد** | `2.147.253.154` در بلوک `2.144.0.0/13` همراه اول | سقف IP روی کاربر واقعی اثر می‌کند، نه روی یک دروازهٔ مشترک |
| **CGNAT در این نمونه نبود** | نشانی عمومی است، نه `100.64.0.0/10` | نگرانی الزام ۲۲ در این نمونه رخ نداد — ولی سقف ۱۰ باقی می‌ماند (یک نمونه دلیل نیست) |
| **IPv6 نداریم** | پاسخ IPv4 روی دیتای موبایل | منطق پیشوند `/64` نوشته می‌شود ولی امروز بی‌استفاده است |
| **وب‌سرور LiteSpeed است، نه Apache** | `SERVER_SOFTWARE` | مسیرهای تخت (`booking.php`) درست‌اند؛ به rewrite تکیه نمی‌کنیم |
| **PHP 8.1.34** | — | با بقیهٔ پروژه یکسان؛ تغییری لازم نیست |

## ۳. تصمیم — تابع نهایی

هیچ هدری باور نمی‌شود. اصلاً فهرست «پروکسی مورد اعتماد» لازم نیست،
چون پروکسی‌ای وجود ندارد.

```php
/**
 * نشانی IP بازدیدکننده، برای سقف نرخ.
 *
 * عمداً هیچ هدر HTTP را نمی‌خواند. پروب ۱۴۰۵/۰۷/۱۴ ثابت کرد که
 * my.mirbolouki.com هیچ پروکسی معکوسی جلوی خود ندارد؛ پس هر
 * X-Forwarded-For که برسد، ساختهٔ خودِ فرستنده است و باور کردنش
 * سقف را به‌کلی بی‌اثر می‌کند.
 *
 * ★ اگر روزی آروان‌کلاد یا کلادفلر جلوی دامنه گذاشته شد، این تابع
 *   باید پیش از آن تغییر کند — به بند «هشدار بازگشت» نگاه کنید.
 */
function booking_client_ip()
{
    return isset($_SERVER['REMOTE_ADDR']) ? $_SERVER['REMOTE_ADDR'] : '';
}

function booking_ip_hash($ip)
{
    $bin = @inet_pton($ip);
    if ($bin !== false && strlen($bin) === 16) {   /* IPv6 → پیشوند /64 */
        $ip = inet_ntop(substr($bin, 0, 8) . str_repeat("\0", 8));
    }
    return hash_hmac('sha256', $ip, IP_HASH_KEY);  /* ۶۴ نویسهٔ هگز */
}
```

## ۴. هشدار بازگشت — خطری که امروز وجود ندارد ولی فردا ممکن است

اگر بعداً CDN جلوی دامنه برود و این تابع عوض نشود، `REMOTE_ADDR`
برای **همهٔ** بازدیدکننده‌ها نشانی CDN می‌شود. آن‌وقت همه یک
`ip_hash` مشترک می‌گیرند و سقف ۱۰ در ساعت **کل مراجعان کلینیک را
با هم قفل می‌کند** — نه یک مهاجم را.

برای همین سقف IP باید در این حالت **باز بماند، نه بسته**:

```php
/* اگر REMOTE_ADDR خصوصی شد، یعنی پروکسی‌ای ظاهر شده که در طراحی
   دیده نشده بود. در این حالت سقف IP را نادیده می‌گیریم و خطا را
   ثبت می‌کنیم. سقف موبایل و سقف روزانه همچنان کار می‌کنند. */
$is_public = filter_var($ip, FILTER_VALIDATE_IP,
                        FILTER_FLAG_NO_PRIV_RANGE | FILTER_FLAG_NO_RES_RANGE);
if ($is_public === false) {
    log_system_error('BOOKING_IP_PROXY_DETECTED', 'REMOTE_ADDR خصوصی است: ' . $ip);
    return true;   /* از سقف IP رد شو؛ قفل‌شدن همه بدتر از نبودِ این لایه است */
}
```

دلیل این انتخاب: سه لایهٔ سقف داریم. اگر یکی از کار بیفتد، دو لایهٔ
دیگر (۳ در ۱۰ دقیقه برای هر موبایل، ۱۰۰ در روز سراسری) هنوز سر جایشان‌اند.
اما اگر لایهٔ IP اشتباهی همه را قفل کند، هیچ‌کس نمی‌تواند نوبت بگیرد و
کسی هم متوجه علتش نمی‌شود.
