۲. دامنهٔ فاز ۳ — دقیقاً چه چیزی ساخته می‌شود

۲.۱ داخل دامنه

  • ثبت یادداشت محرمانه توسط درمانگر روی پرونده‌های خودش
  • مشاهدهٔ یادداشت‌های خودِ نویسنده، به ترتیب زمانی
  • ویرایش یادداشت در یک پنجرهٔ زمانی محدود (بند ۵.۳)
  • ابطال منطقی یادداشت (بدون حذف فیزیکی)

  • فعال شدن دکمهٔ «مشاهده پرونده» که از فاز ۱ غیرفعال بود
  • ثبت کامل حسابرسی برای هر اقدام روی یادداشت

۳. جدول تازه — یک جدول، هفدهمین جدول سامانه

CREATE TABLE confidential_notes (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    public_id VARCHAR(30) NOT NULL UNIQUE,
    clinical_case_id BIGINT UNSIGNED NOT NULL,
    author_person_id BIGINT UNSIGNED NOT NULL,
    body MEDIUMTEXT NOT NULL,
    session_date DATE NULL,
    appointment_id BIGINT UNSIGNED NULL,
    is_void TINYINT(1) NOT NULL DEFAULT 0,
    void_reason VARCHAR(255) NULL,
    created_at_utc DATETIME NOT NULL,
    updated_at_utc DATETIME NULL,
    edit_count INT UNSIGNED NOT NULL DEFAULT 0,
    CONSTRAINT fk_notes_case FOREIGN KEY (clinical_case_id)
        REFERENCES clinical_cases(id) ON DELETE RESTRICT ON UPDATE RESTRICT,
    CONSTRAINT fk_notes_author FOREIGN KEY (author_person_id)
        REFERENCES persons(id) ON DELETE RESTRICT ON UPDATE RESTRICT,
    CONSTRAINT fk_notes_appointment FOREIGN KEY (appointment_id)
        REFERENCES appointments(id) ON DELETE RESTRICT ON UPDATE RESTRICT,
    KEY idx_notes_case_author (clinical_case_id, author_person_id, is_void),
    KEY idx_notes_author_created (author_person_id, created_at_utc)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

۴.۲ قاعدهٔ پیاده‌سازی — بدون استثنا

هر پرس‌وجوی خواندن یادداشت باید هر دو شرط را هم‌زمان داشته باشد:

WHERE clinical_case_id = ?        -- پرونده
  AND author_person_id = ?        -- و نویسنده = کاربر واردشده

شرط دوم از $_SESSION['person_id'] می‌آید، نه از پارامتر ورودی کاربر. هیچ تابعی نوشته نمی‌شود که یادداشت را فقط با public_id و بدون شرط نویسنده برگرداند — حتی برای استفادهٔ داخلی. این یک قاعدهٔ معماری است، نه سلیقه.

افزون بر آن، پیش از هر اقدام بررسی می‌شود که clinical_cases.responsible_therapist_person_id برابر کاربر واردشده باشد.

۵. قواعد رفتاری

۵.۱ پیش‌شرط ثبت یادداشت

یادداشت فقط روی پرونده‌ای ثبت می‌شود که وضعیت آن ACTIVE و درمانگر مسئولش کاربر واردشده باشد.

۵.۲ اتصال اختیاری به نوبت

درمانگر می‌تواند یادداشت را به یکی از نوبت‌های گذشتهٔ همان مراجع با همان درمانگر متصل کند. فهرست نوبت‌ها از فاز ۲ خوانده می‌شود و فقط نوبت‌های COMPLETED قابل انتخاب‌اند. انتخاب از فهرست کشویی است — طبق الزام ثابت پروژه هیچ تاریخی تایپ نمی‌شود.

۵.۳ پنجرهٔ ویرایش

یادداشت تا ۲۴ ساعت پس از ثبت قابل ویرایش است. پس از آن فقط ابطال ممکن است و درمانگر باید یادداشت تازه بنویسد.

دلیل: یادداشت بالینی یک سند است. ویرایش نامحدود گذشته، ارزش سندیت را از بین می‌برد. عدد ۲۴ ساعت یک قاعدهٔ کسب‌وکار است و در صورت نظر متفاوت مالک تغییر می‌کند.

۵.۴ ابطال

ابطال نیازمند ذکر دلیل است. یادداشت باطل‌شده در فهرست با نشان «باطل‌شده» و متن محوشده دیده می‌شود، اما از پایگاه داده حذف نمی‌شود.

۵.۵ اعتبارسنجی متن

حداقل ۱۰ و حداکثر ۲۰٬۰۰۰ نویسه. ذخیره با prepared statement، نمایش با htmlspecialchars طبق قواعد امنیتی ثابت پروژه.

۸. ریسک‌های پذیرفته‌شده — صادقانه

این سه مورد پیامد مستقیم تصمیم‌های ۱ و ۲ مالک‌اند. ساخته‌شدنشان ممکن نیست؛ فقط باید آگاهانه پذیرفته شوند.

#ریسکتوضیحکاهش‌دهنده
P1نسخهٔ پشتیبان پایگاه داده حاوی متن خام یادداشت استچون رمزنگاری نداریم، هر فایل .sql پشتیبان، یادداشت‌های بالینی را به‌صورت خوانا دارد. اگر این فایل روی رایانهٔ شخصی، ایمیل یا فضای ابری قرار گیرد، محرمانگی از بین رفته استرویهٔ مکتوب نگهداری پشتیبان؛ هرگز دانلود روی دستگاه مشترک؛ حذف پس از استفاده
P2کنترل دسترسی فقط در لایهٔ نرم‌افزار استهر کسی که به phpMyAdmin یا کاربر پایگاه داده دسترسی داشته باشد — از جمله خودِ مدیر سامانه و پشتیبانی هاست — می‌تواند یادداشت‌ها را بخواند. جملهٔ «مدیر یادداشت را نمی‌بیند» فقط دربارهٔ داخل سامانهٔ جوما درست استمحدود نگه‌داشتن دسترسی cPanel؛ شفاف بودن این محدودیت برای درمانگران
P3گسست تداوم درمانبا قاعدهٔ «فقط نویسنده»، اگر مراجع به درمانگر دیگری ارجاع شود یا درمانگر از کلینیک برود، یادداشت‌های پیشین برای هیچ‌کس قابل خواندن نیست. داده باقی می‌ماند ولی عملاً غیرقابل استفاده استباید آگاهانه پذیرفته شود. اگر روزی لازم شد، نیازمند تصمیم تازهٔ مالک است
P3 مهم‌ترین نکته‌ای است که از شما می‌خواهم دوباره دربارهٔ آن فکر کنید. پیاده‌سازی «فقط نویسنده» کاملاً ممکن است و طبق خواستهٔ شما انجام می‌شود؛ اما پیامد عملی‌اش این است که سابقهٔ درمانی با رفتن یک درمانگر عملاً از دسترس خارج می‌شود. تغییر این تصمیم بعداً هزینهٔ فنی ندارد (فقط شرط پرس‌وجو عوض می‌شود)، ولی یادداشت‌هایی که با این فرض نوشته شده‌اند، با انتظار محرمانگی مطلق نوشته شده‌اند و بازکردن بعدی دسترسی، نقض آن انتظار است.

۹. آزمون‌های الزامی فاز ۳

طبق رویهٔ فاز ۲، این آزمون‌ها باید واقعاً اجرا شوند. بررسی نحوی کد اجرا نیست و هیچ آزمون اجرانشده‌ای «قبول» اعلام نخواهد شد.

#آزمونانتظار
N1درمانگر الف یادداشت می‌نویسد؛ درمانگر ب با دستکاری public_id در URL تلاش می‌کند بخواندرد با پیام «دسترسی مجاز نیست» + ثبت NOTE_ACCESS_DENIED
N2مدیر مستقیماً آدرس صفحهٔ یادداشت را باز می‌کندرد؛ وراثت نقش نباید راه دهد
N3منشی همان کار را می‌کندرد
N4ویرایش یادداشت ۲۵ ساعتهرد با پیام روشن؛ فقط ابطال ممکن
N5ابطال یادداشتاز دید پنهان نمی‌شود، با نشان «باطل‌شده» می‌ماند؛ در پایگاه داده باقی است
N6اتصال یادداشت به نوبت یک مراجع دیگر با دستکاری فرمرد
N7متن یادداشت در audit_log جست‌وجو شودیافت نشود
N8اجرای دوبارهٔ upgrade_phase3.phpبدون خطا، بدون جدول یا دادهٔ تکراری
N9سلامت فاز ۱ و ۲ پس از ارتقاورود، تعویض نقش، پذیرش، نوبت‌دهی و تقویم دست‌نخورده
یادآوری: محیط توسعه PHP و MySQL ندارد، بنابراین مانند فاز ۲ این آزمون‌ها فقط روی سرور قابل اجرا هستند. ریسک R8 فاز ۲ (نبود محیط Staging) همچنان باز است و برای N8 ضروری خواهد بود.
